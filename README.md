# Lazoo

Lazoo is a Windows-first, local desktop control plane for a personal team of native coding-agent harnesses. It is intended to coordinate Codex, Claude Code, GitHub Copilot, OpenCode, Grok Build, and Antigravity employees without replacing or flattening their native environments.

The name is a deliberately silly blend of **lazy** and **zoo**: wake the right employee when work arrives, let the team coordinate, and keep the menagerie under control.

## Status

[Provider accounts and GitHub Copilot](docs/ACCOUNT-ROUTING.md) describes isolated
native profiles, protected API keys, per-provider routing policies, and the compatible
streaming API pool. Configure them under **Settings → Accounts** or `lazooctl account`.

Backend preparation for UI implementation is tracked in
[the integration guide](docs/UI-BACKEND-HANDOFF.md) and
[the current handoff](docs/NEXT-SESSION.md). They distinguish supported launch
capabilities, recoverable failures, history paging and terminal attachment from
the remaining full-product and native-TUI gates. The desktop binding is still
separate work.

The first Windows control-plane slice, polished read-only desktop shell, native-provider adapters, durable employee roster, native-session ownership, collaboration bus, conversation/turn delivery, schema-7 automatic task dispatch, the schema-8 approval gate, Codex collaboration tools, the schema-9 incident ledger, lead notice delivery, peer messaging tools, coalesced notice turns, the schema-10 activation policy, schema-11 idle suspension, schema-12 bounded lead remediation, schema-13 user notifications, schema-14 message priority, and schema-15 configurable thresholds are implemented. Lazoo provides five native executables:

- `lazoo-desktop.exe` opens the slate, keyboard-first Tauri 2 desktop: a projects-first sidebar (each registered project with its conversations, then Home's recents), a launcher per space with the team and starter suggestions, a one-time setup that offers recommended agents for the detected harnesses, one conversation surface with the lead and its workers as tabs, supported harnesses' genuine native TUIs through the daemon's read-only view (xterm.js) or Lazoo's own transcript of the durable turns, the attention strip and Inbox for what needs you, Settings, and a command palette; see `docs/superpowers/specs/2026-11-01-desktop-ui-refresh-design.md` and `docs/superpowers/specs/2026-10-31-desktop-ui-pilot-design.md`.
- `lazoo-keeper.exe` supervises the daemon with a bounded restart policy and emergency spool.
- `lazood.exe` owns the SQLite WAL store, revisioned employee roster, native-session lifecycle, collaboration-message, conversation/turn, and task/evidence ledgers, and authenticated named-pipe API.
- `lazooctl.exe` exposes status, project registration/listing, event listing/following, native-provider diagnostics, employee/roster/session/message/conversation/turn/task control, and planned shutdown.
- `lazoo-session-host.exe` is the protocol-transparent launch gate that places each native provider tree in its daemon-owned Windows Job Object before provider startup.

The desktop sends only the actions the daemon offers as data (approve, decline, accept, cancel, resolve, rename, cancel-turn, retry-turn, stop-session, start, native trust) through a Rust allowlist; it never names an executable. Backend adapters connect Codex App Server, GitHub Copilot ACP, OpenCode ACP, Grok Build ACP, Antigravity stream JSON, and Claude Code stream JSON without flattening native configuration or authentication. Schema 7 adds durable dispatch ownership and workspace evidence to the task tree. Accepted Codex child tasks wake automatically when their assigned worker is free, reuse the one canonical delegation message, and start only after native acceptance or durable progress. Projectless tasks use owner-protected private directories; project tasks use deterministic retained Git worktrees and never mutate dirty canonical checkout files. Configuration drift and pre-provider restart fail atomically, possible in-flight restart becomes `uncertain`, and task cancellation interrupts an accepted native turn. Schema 8 adds the durable approval ledger: Codex command-execution and file-change approval requests are recorded first, answered by policy under `self-decision` and `full-autonomy`, and held for the local user under `ask`. Pending approvals expire, cancel with their turn, and fail closed on restart; the provider is always answered `decline` when no approval exists. Every daemon-managed Codex session also receives four Lazoo collaboration tools (`employees_list`, `task_delegate`, `task_wait`, `task_report`; the brief's dotted names, spelled with underscores because the Codex Responses API rejects dots) through the app-server dynamic-tool surface, so a lead can read the live roster, delegate child tasks, wait for their evidence, and report structured outcomes from inside its native session; each call acts only as the turn's own employee and session and goes through the same fail-closed task guards as the CLI. Schema 9 adds the human-readable incident ledger: session start failures, provider stalls and rejections, dead letters, dispatch failures, restart owner loss, and keeper emergency records fold into one incident per code, employee, and project, three equivalent failures inside five minutes promote it to `priority`, only the local user acknowledges or resolves it, and employees read and report incidents through `incident_list` and `incident_report`. Lead notice delivery closes the loop back to the lead without a schema change: a child task that reaches a terminal state and an incident promoted to `priority` become durable `result` and `status` notices addressed to the lead of the task tree, delivered as one provider turn each on the lead's idle session, consumed directly when the lead is already inside `task_wait`, and held while the lead is dormant until the local user resumes it; a notice never starts a provider process. Peer messaging rides the same path without a schema change: `message_send` and `message_reply` let an employee ask another employee in its task tree a question and answer one, each message links both tasks and threads under the message it answers, a recipient reads it inside its own `task_wait` or `message_send` wait or as one turn on its idle session, a peer turn never completes the recipient's task, and a dormant recipient is never activated. Coalesced notice turns deliver every notice and peer message queued for one recipient and task as a single turn, oldest first, each keeping its own acknowledgement evidence; a single notice is delivered exactly as before. The schema-10 activation policy lets the user opt one employee into bounded automatic activation: a recorded notice turn may start one session for a dormant `notice-turns` recipient, deliver that turn on the recipient's own task, and stop the session; `manual`, the default, still waits for the user. Schema-11 idle suspension lets the user give an employee an idle timeout: the daemon stops that employee's idle session once no turn has touched it for the whole timeout, never while a turn on it is unfinished; 0, the default, keeps a warmed session up until the user stops it. Schema-12 bounded lead remediation finishes the brief's escalation path: an incident promoted on a child task opens a five-minute window in which the lead of that task tree may apply at most two remedies through a ninth tool, `incident_remedy` (`cancel-task` the affected child, or `redelegate-task` a failed or cancelled child's objective through the ordinary delegation guards); a refused remedy uses no attempt, and when the window closes, anything the lead's remedy did not stop recurring, and any promoted incident with no lead to remediate it, becomes a priority notification for the user (`escalation: user`). Only the user resolves an incident, and escalation never retries, restarts, or cancels anything. The brief's section 14.2 default thresholds now apply per code: a stalled session, a daemon crash, or an employee process that dies while it holds assigned work is promoted by its first occurrence, and unexpected exits of the same employee process by their second; every other code still needs three inside five minutes. Schema 13 tells the user: every open incident that reaches `escalation: user` is announced at most once with the same Windows notification the keeper already uses, one notification per 15-second pass (the incident itself, or a count when several arrive together), never retried, and never repeated for a crash the keeper already announced. The two tool waits that hold a model turn, `task_wait` and a `message_send` waiting for its reply, now wake on the daemon's own store write (a child's completion, a peer question, a reply, a cancelled turn) instead of re-reading the store every 250 ms, with the same deadlines and evidence. Schema 14 gives every message a `priority` (`normal` or `priority`): the notice that tells a lead about a promoted incident is always `priority`, the local user may send one with `lazooctl message send --priority`, and the collaboration tools cannot set it. One dead-lettered priority message is promoted at once (section 14.2), whatever exhausted it: `message.fail` raises `LZ-MESSAGE-DEADLETTER` immediately, and the 15-second sweep raises it for a priority notice lost to a failed notice turn, a failed dispatch, or a restart, before it closes remediation windows and tells the user. Priority does not change delivery order. Schema 15 makes section 14.2's thresholds the user's to tune: `lazooctl incident threshold set <CODE> --occurrences N [--window-seconds S]` overrides one code (1 to 100 occurrences inside one minute to one day), `reset` returns it to the default, and `list` shows every described code with its effective threshold and whether it is configured. A change applies from the next occurrence and never demotes a promoted incident; an employee death under assigned work and a dead-lettered priority message still promote at once whatever is configured, and no collaboration tool can read or set a threshold. The desktop Inbox read model is served without a schema change: `inbox.list` and `inbox.counts` (`lazooctl inbox list|counts`) derive on every call what needs the user from the approval, task, and incident ledgers, so a pending approval, a `proposed` or `uncertain` task, and an open incident escalated to the user are `action-required` and count toward the rail badge, a lead's remediation window is `watching` with its deadline, an acknowledged escalation stays visible but uncounted, and what left the list is the `resolved` archive paged newest first with an opaque cursor; every item carries its row's `id`, `revision`, and `state`, Lazoo's own title and required action, a deep-link scope, and its applicable actions as data naming the existing revision-checked RPC, and the result names the event high-water mark to subscribe from. Nothing is stored, no new mutation exists, and no collaboration tool can read it. Resource accounting (brief section 20) is displayed without a schema change: `system.resources` (`lazooctl system resources`) reports the daemon's own CPU time, working set and peak, handle count, uptime, and live session count, and `session.resources` (`lazooctl session resources <id>`) reports a live session's native process tree from the Job Object Lazoo already owns for it (active and total processes, CPU time, peak process and job memory), refusing a session that is not live in this daemon; both are point samples, nothing is stored or enforced, a provider's use is reported beside the daemon's and never counted against it, and `desktop.snapshot`, `system.status`, and `session.show` are unchanged. The desktop workspace read models are served without a schema change: `workspace.conversations` and `workspace.launcher` (`lazooctl workspace conversations|launcher`) derive a space's conversation history with its markers and remembered lead and the launcher's startable leads with the start request as data, and `workspace.conversation` (`lazooctl workspace show <id>`) derives the active conversation's lead header (identity, the root task's authority, the lead's session and private working directory, and a truthful lifecycle: dormant, starting, busy, idle, stopping, suspended, failed, or unknown), one worker dock card per delegated task in the information architecture's eight states (unknown, needs-approval, interrupted, failed, complete, blocked, running, waiting, in that order of precedence, each with Lazoo's words), the conversation's own unresolved Inbox items, and its newest turns bounded by a limit; the header and each card also name the actions their rows allow right now (accept, cancel, resolve, the approval's decisions, cancel-turn, retry-turn, stop-session, rename) as data for an existing revision-checked RPC, exactly as Inbox items do; nothing is stored, no event or new mutation exists, naming an RPC grants nothing, and no collaboration tool can read it. The earlier authorized live conversation gate completed with exact `LAZOO_TURN_OK`; the automatic-dispatch, approval-gate, collaboration-tools, minimum-incidents, result-delivery, peer-messaging, coalesced-notices, activation-policy, idle-suspension, lead-remediation, incident-thresholds, user-notifications, message-arrival, message-priority, configurable-thresholds, desktop-inbox, resource-accounting, conversation-rename, provider-config-discovery, core-scenario, workspace-read-models, workspace-conversation, workspace-actions, provider-migration-preview, and claude-full-autonomy acceptances are deterministic and did not invoke a live model. Claude Code employees now receive conversation turns and dispatched tasks under `full-autonomy` only, the one authority its prompt-free `auto` mode enforces natively; under `ask` and `self-decision`, and for Antigravity, OpenCode, and Grok Build under any authority, delivery still fails closed before any provider I/O (`LZ-TASK-AUTHORITY-UNSUPPORTED`, `LZ-TURN-PROVIDER-UNSUPPORTED`), and no support is claimed until a live Claude Code gate runs. Schema 16 to 18 add owner-managed ConPTY terminals with a separate authenticated byte pipe (`lazooctl terminal`), compressed canonical turn archives with quotas and recoverable intents, a typed FTS memory ledger with scoped retrieval and bounded context injection (`lazooctl memory`), an opt-in native summary worker (`lazooctl memory-worker`), selected Codex MCP configuration preview, apply, show, and rollback (`lazooctl provider config-preview`, `config-apply`, `config-rollback`), ACP and Claude Code per-action approval bridging into the one-action approval observer, bounded control IPC admission, and a shared infrastructure Job Object with a 20% CPU cap and 15% background throttling (`lazooctl system budget`); provider trees and the desktop stay outside that job. Codex, OpenCode, Antigravity, and Claude Code (through the restored native subscription) each passed a short live prompt, stream, and completion smoke on 2026-10-15 and 2026-10-16, and on 2026-10-17 each passed its live readiness probe, model-backed turn, resume where supported, and daemon smoke, while Claude Code also passed a full live lifecycle (messaging, cancellation, resume on wake, planned shutdown) through `scripts/acceptance/provider-live-lifecycle.ps1 -Provider claude-code`; Grok Build is excluded from core v1; live cancellation on the other three providers and permissions under `ask` remain fixture-proven or refused by design. Schema 19 retains the redacted raw provider frames of every completed turn as a second archive kind inside the same quota (`memory.cleanup.preview` names both kinds). Every `lazooctl` request wait is bounded (5 s write, 20 s read-only response, 600 s otherwise, `LZ-IPC` exit 3 naming the phase) and the governor initialization lock gives up after 5 s. `lazooctl session attach <id>` opens an owner terminal that resumes a suspended Claude Code or Codex session's native TUI. A suspended Claude Code session is resumed on its next activation (user turn, notice turn, or `session.warm`) at the same configuration revision in its prior working directory and audited as `session.resumed`; Codex starts fresh and records `session.resume.skipped` (`codex-dynamic-tools`), because `thread/resume` cannot carry Lazoo's collaboration tools in any installed codex-cli. Cancellation is proven deterministically for every adapter, and core scenario step 12 passes through the real memory worker pipeline. OpenCode employees receive conversation turns and dispatched tasks under every authority: `full-autonomy` launches prompt-free with a per-launch `OPENCODE_PERMISSION` block of `{"*":"allow"}`, while `ask` and `self-decision` launch with `{"*":"ask"}` plus native allows for the read-only tools only, so every command, file write, delete, or move reaches the one-action approval ledger (the Inbox under `ask`, policy under `self-decision`, where the ACP bridge marks every request a scope expansion and so still asks the user), and network, connector, and unknown tool kinds are declined one-shot with a recorded reason; a full-autonomy session never serves a narrower turn. ## Build and run

Install and build the checked-in desktop frontend before the locked Rust release build:

```powershell
npm --prefix apps\lazoo-desktop\ui ci
npm --prefix apps\lazoo-desktop\ui run build
cargo build --workspace --release --locked
& .\target\release\lazoo-keeper.exe
```

Open the desktop from another terminal:

```powershell
& .\target\release\lazoo-desktop.exe
```

The shell reconnects every ten seconds and keeps the last successful snapshot visible if the daemon becomes unavailable. It does not start or stop the keeper. The companion CLI remains available for control operations:

```powershell
& .\target\release\lazooctl.exe status
& .\target\release\lazooctl.exe project register C:\path\to\git-repository
& .\target\release\lazooctl.exe project list
& .\target\release\lazooctl.exe events list
& .\target\release\lazooctl.exe provider list
& .\target\release\lazooctl.exe provider probe codex
& .\target\release\lazooctl.exe provider config
& .\target\release\lazooctl.exe provider preview
& .\target\release\lazooctl.exe employee create Rhea --provider codex --role Lead
& .\target\release\lazooctl.exe employee list
& .\target\release\lazooctl.exe roster show
& .\target\release\lazooctl.exe roster refresh
$employeeId = '<employee-uuid>'
$sessionId = '<session-uuid>'
& .\target\release\lazooctl.exe session warm $employeeId --expected-employee-revision 1
& .\target\release\lazooctl.exe session list
```

Add `--json` for a stable machine-readable result. Mutable state defaults to `%LOCALAPPDATA%\Lazoo`; set `LAZOO_DATA_ROOT` to isolate a test installation.

`provider config` is read-only configuration discovery (brief section 16.1, steps 1 to 5): it reads each provider's known configuration file (`~/.codex/config.toml` or `CODEX_HOME`, `~/.claude.json`, `~/.config/opencode/opencode.json`), parses only the MCP-server shapes Lazoo knows, reports every integration with its transport, command or URL, enabled flag, and the names (never the values) of the environment variables and headers the provider sends, hashes each to one identity, and names exact duplicates and same-name conflicts across providers; a missing file is a fact, a malformed one is reported without being quoted, Grok Build and Antigravity are reported as unsupported, and nothing is written. `provider preview` is step 6, the migration preview over that discovery: one candidate per distinct integration with a proposal (`manage` when one provider holds it, `merge` when several hold the same identity, `choose` when another integration shares its name with a different identity, as section 16.3 requires an explicit choice or a provider-specific alias) and Lazoo's words for it, its sources, the providers that already hold it and those that do not, the secret key names (never a value), and a summary; nothing is selected, written, or stored, and step 7 and section 16.2 (selection and apply) wait for the owner's design. `provider list` performs discovery only and never launches a provider. `provider probe <provider>` launches a bounded, non-model native readiness check. A model-backed diagnostic is always explicit because it may consume provider quota:

```powershell
& .\target\release\lazooctl.exe provider smoke codex --prompt "Reply with exactly LAZOO_CODEX_OK. Do not use tools."
```

Provider names are `codex`, `opencode`, `grok-build`, `antigravity`, and `claude-code`. Provider failures use the `LZ-PROVIDER-*` RPC family and CLI exit code 8. Provider diagnostics are intentionally absent from `desktop.snapshot`; no desktop UI was added for this slice.

`employee create` performs one bounded non-model readiness probe, then stores the named employee and safe normalized provider evidence transactionally. `employee list`, `employee show`, and `roster show` are read-only and never launch a provider. `roster refresh` explicitly reruns one non-model probe per enabled provider; it never invokes a model smoke. Employee conflicts and stale revisions use the `LZ-EMPLOYEE-*` RPC family and CLI exit code 9. `employee create --activation-policy` and `employee update --activation-policy` set `manual` (the default) or `notice-turns`, and `--idle-timeout-seconds` sets how long an idle session may stay quiet before the daemon suspends it (60 to 86400 seconds, or 0, the default, for never); each change is revisioned like every other employee setting and refused while the employee has an active session. Idle suspension ends the native thread, so the next user turn or `notice-turns` activation starts a fresh session. Employee and roster fields remain absent from `desktop.snapshot`.

`session warm` is the only session command that launches a provider. It requires the employee configuration revision, records `starting` before launch, and returns only after the provider-native session reports an ID and owned host PID; it does not send a turn. Warm and stop are idempotent. Stop is revision-checked and bounded, while prior-boot active sessions reconcile to `failed` with `LZ-SESSION-OWNER-LOST` instead of adopting a PID. Session failures use CLI exit code 10. Session and roster fields remain absent from `desktop.snapshot`.

`message send` records an immutable version-1 envelope and queued delivery state before any attempt; `--priority` marks it `priority`, so one dead letter of it is a priority incident. Claim, acknowledge, fail, retry, and cancel are idempotent and revision-checked; exhausted attempts create durable dead-letter evidence, and prior-boot delivering attempts reconcile with `LZ-MESSAGE-OWNER-LOST`. Message failures use CLI exit code 11. These controls do not activate a provider, send a model turn, or expand `desktop.snapshot`.

`conversation rename <id> --expected-revision N [--title T]` sets or clears a conversation's title at the revision the user saw (the information architecture makes titles user-editable); the same title again changes nothing and emits no event, a different title at a stale revision is `LZ-CONVERSATION-STALE` with the current revision, and every rename is a `conversation.renamed` event. `conversation create` and `turn submit/retry/cancel/list/show` use the schema-7 conversation ledger and actor-aware version-2 envelopes. User-authored submission may explicitly activate the selected Codex lead with `--activate-if-needed`; employee-authored turns cannot activate dormant recipients. Native turn IDs or observed progress are required before message acknowledgement, accepted turns are never retried automatically after uncertainty, and provider terminal states remain distinct from canonical delivery truth. Conversation/turn failures use CLI exit code 12.

`task delegate/accept/start/report/cancel/resolve/list/show` operates on the durable schema-7 task graph. Root task identity is the creating user-turn identity; child depth is capped at four and nonterminal direct fan-out at eight. Authority is the most restrictive of parent, request, and assignee. Accepted non-ask children and user-accepted proposals are claimed once by the daemon, dispatched when their worker is free, and expose dispatch/workspace evidence through `task show`. Native evidence, revision checks, actor/session checks, cancellation, descendant blocking, and owner-loss uncertainty fail closed. Git worktrees are retained for audit; cleanup is intentionally not automatic. Task failures use CLI exit code 13. Task controls are daemon/CLI-only and do not expand `desktop.snapshot`.

`approval list/show/approve/decline` operates on the schema-8 approval ledger. When a daemon-managed Codex turn asks to run a command or change files, Lazoo records the request first and applies the linked task's effective authority: `ask` holds the provider until the local user decides, `self-decision` approves in-scope work by policy and holds scope expansions, and `full-autonomy` approves by policy. A decision is bound to one approval and revision; there is no session-wide grant. Pending approvals expire after fifteen minutes, close when their turn is cancelled, and close with `LZ-APPROVAL-OWNER-LOST` on restart, and every closure answers the provider `decline`. Approval failures use CLI exit code 14. Approval controls are daemon/CLI-only and do not expand `desktop.snapshot`.

Codex collaboration tools need no CLI command: the daemon declares `employees_list`, `task_delegate`, `task_wait`, and `task_report` to every Codex session it starts, and the model calls them natively. `task_delegate` must cite the `rosterRevision` returned by `employees_list`, never widens authority, and creates a `proposed` task under `ask` that waits for `lazooctl task accept`; otherwise the child is accepted and dispatched automatically. `task_wait` blocks for at most ten minutes and returns each child's state, failure, and native output. `task_report` records progress, completion, or failure for the caller's own task. Refused calls answer the model a stable `LZ-TOOL-*` or `LZ-TASK-*` code without ending the turn, and a session without the daemon attached answers `LZ-TOOL-UNATTACHED`. Tools are declared only for Codex and only on `thread/start`.

`incident list/show/acknowledge/resolve` operates on the schema-9 incident ledger. The daemon raises an incident right after it commits a session start failure, a provider rejection, stall, timeout, exit, or missing completion evidence, a dead letter, a dispatch failure, or restart owner loss, and folds keeper emergency records in at startup. Equivalent failures share one row whose occurrence counters advance; three inside five minutes promote it to `priority`, except that `LZ-SESSION-STALLED`, `LZ-DAEMON-UNAVAILABLE`, and an `LZ-PROCESS-EXIT` tied to a task are promoted by their first occurrence and any other `LZ-PROCESS-EXIT` by its second (brief section 14.2); a promotion's event is always `incident.escalated`. Each incident carries a plain-language title, explanation, and next action, the linked employee, project, task, session, turn, and message ids, and bounded detail with the raw failure code. Acknowledging and resolving are revision-checked and idempotent; a new occurrence reopens an acknowledged incident, and a resolved one never reopens. Employees see their project's open incidents through `incident_list` and record their own through `incident_report`. Incident failures use CLI exit code 15. Incidents never retry work, change authority, or expand `desktop.snapshot`.

Schema 12 bounds the lead's response to a promoted incident. When an incident about a direct child of an active root task is promoted, it carries `escalation: lead` and a `remediationDeadlineAt` five minutes later, and the lead's `status` notice names that deadline. Inside the window the lead may call `incident_remedy` at most twice for that incident: `cancel-task` cancels the affected child as the lead (an in-flight dispatch turn is asked to cancel, exactly as `task cancel` does), and `redelegate-task` sends a failed or cancelled child's objective out again to `employeeId` (default: the same employee) citing `rosterRevision`, through every delegation guard, so `ask` authority still proposes the new task for the user. Each remedy commits with its action in one transaction and is listed under the incident's `remedies`; a refused remedy (`LZ-INCIDENT-REMEDY-CLOSED`, `-SCOPE`, or `-TARGET`, or any task guard) consumes no attempt. The daemon's 15-second sweep closes the window: an incident that has not recurred since the lead's last remedy becomes `remediated`, and everything else unresolved becomes `escalation: user` with an `escalationReason` (`no-remedy`, `remedies-exhausted`, `recurred-after-remedy`); a recurrence after the second remedy or after a remediated window reaches the user at once, and an incident promoted with no lead to remediate it, or promoted before schema 12, goes to the user immediately (`no-lead`, `schema-upgrade`). `lazooctl incident list --escalation user` lists the priority notifications, and the daemon announces each open one on the Windows desktop at most once (`userNotification`: `shown`, `failed`, `keeper` when the keeper already announced it, or `claimed` when the daemon stopped mid-announcement). The lead never resolves or acknowledges an incident, and nothing in the window retries, restarts, re-authenticates, or changes authority.

`system resources` and `session resources <id>` display resource use (brief section 20) as point samples read from Windows on request: the daemon's own process (CPU time, working set and peak, handle count, uptime, live sessions) and a live session's native process tree from its Job Object (active and total processes, CPU time, peak process and job memory). A session that is not live in this daemon is refused with `LZ-SESSION-NOT-LIVE`; nothing is stored, no limit is set on any job, and a provider's use is never counted against Lazoo's own.

`workspace conversations [--project-id]` and `workspace launcher [--project-id]` are the first two desktop workspace read models (phase 1 of the workspace contract), derived on every call and never stored: one space's conversation history newest first, each with a title (stored, else the first request's first line, else "New work"), a marker that follows its rows (`needs-attention`, `active`, `failed`, `completed`, or none) with Lazoo's words, worker counts, the newest root's and last turn's states, the last terminal time, and the space's remembered lead; and, for the launcher, every employee as a lead candidate with its availability, whether a start would succeed now and why not, the remembered lead, the authority modes, and the start request as data for `conversation create` then `turn submit`. `workspace show <id> [--turn-limit]` is phase 2: the active conversation's lead header (employee, role, harness, model, the root task's effective authority, availability, the latest session with its private working directory, a truthful lifecycle, and the unfinished turn if any), the root task, the newest turns oldest first with a truncation flag, one worker card per task below a root (label, the dock state with Lazoo's words beside the task's own state, authority, session, active turn, dispatched workspace, failure, and times), and the conversation's own unresolved Inbox items as `attention`; completed cards stay in the list for the desktop to dismiss locally. Phase 3 adds `actions` to the header (`rename` always, with the caller's `title`; `cancel-turn` for the lead's unfinished or retryable turn; `retry-turn` for a retryable one while the lead's session is idle and owned by this daemon; `stop-session` for an idle lead session with no unfinished turn) and to each card (`accept` and a user `cancel` for a proposal; `resolve-*` for an uncertain task; the pending approval's `approve` and `decline`; `cancel` for a waiting or running task with no unfinished descendant; nothing once terminal or already cancelling), each naming the RPC and the `expectedRevision` the user saw; the caller adds a fresh `idempotencyKey` and sends exactly that request, and every named RPC keeps its own guards. `inbox list/counts` is the desktop Inbox read model, derived on every call and never stored. `inbox list --filter all|approvals|permissions|incidents|resolved` returns the items the user must act on first (a pending approval, a `proposed` task waiting for `task accept`, an `uncertain` task waiting for `task resolve`, an open incident escalated to the user), then a lead's remediation window as `watching`, then acknowledged escalations; `resolved` is the archive, newest change first, paged with `--before <nextBefore>`. `inbox counts` is the rail badge: `unresolved` counts only `action-required` items, `approvals` includes proposals, `watching` is never on the badge, and `permissions` stays 0 until terminal permission passthrough exists. Each item names its applicable actions as data (`approval.decide`, `task.accept`, a user `task.cancel`, `task.resolve`, `incident.acknowledge`, `incident.resolve`) with the `expectedRevision` the user saw; the caller adds an idempotency key and sends exactly that request. No collaboration tool can read the Inbox.

Lead notices need no CLI command either. When a child task reaches `completed`, `failed`, `cancelled`, or `uncertain` by any path, the daemon queues one `result` message from the worker to the employee that owns the parent task, threaded under the delegation, carrying the state, failure, native output bounded to 16 KiB, and the count of unfinished siblings. When an incident about a child task is promoted to `priority`, it queues one `status` message to the lead of the tree. Every notice queued for the lead's task is delivered as a single provider turn on the lead's idle session, oldest first under one header when several are waiting, under the lead task's effective authority and only while no other turn on that task is unfinished; each notice keeps its own acknowledgement evidence, a turn carrying only peer messages never completes the task, and a lead already inside `task_wait` receives the outcome there with the notice acknowledged with that turn as evidence. A dormant lead under the default `manual` activation policy is never activated by a notice: it stays queued with its turn recorded until `lazooctl session warm` or a new user turn resumes the lead. A lead whose `activationPolicy` is `notice-turns` is activated by the daemon for that one recorded turn: one session keyed to the turn, the turn delivered on the lead's own task, and the session stopped when the turn ends; a refused start raises an incident and is never retried for the same turn, which then waits for the user. Notices about the lead itself, about the root task, or on a terminal tree are never sent, and `lazooctl message list` shows every notice and its delivery state.

Peer messages need no CLI command either. Inside a Codex turn, `message_send` sends up to 16 KiB of text to another employee that has an accepted or running task in the caller's task tree (the lead or a sibling), and `message_reply` answers a message the caller received by citing its id; the daemon fixes the sender to the turn's own employee and session, links the sender's and recipient's tasks, and threads a reply under the message it answers. A recipient reads peer messages inside its own `task_wait` (which returns early with `messages` so a lead can answer and wait again) or inside its own `message_send` wait (`waitForReplySeconds`, at most ten minutes, returns the `reply` inline), or, when it is idle with a running task, as one provider turn on its existing session. A peer turn only progresses the recipient's task, never completes it, so a question delivered just before a child's result cannot lose that result. A dormant recipient is activated only by its own `notice-turns` policy, once per recorded turn; under the default `manual` policy the message stays `queued` until the local user resumes it, and a message whose recipient task ends first is closed as `cancelled`, which a waiting sender sees at once. Refused sends and replies (to oneself, outside the tree, empty or oversized text, or a message not addressed to the caller) answer `LZ-TOOL-INVALID` or `LZ-TOOL-SCOPE` without ending the turn, and a peer message is never an approval and never changes task ownership, authority, or permissions.

## Operating boundary

- Windows first
- One local user
- Native provider sessions and terminals
- Git worktrees by default for editing assignments
- Configurable authority, with `ask` as the default
- Local control plane with no network listener by default
- Read-only desktop snapshot; control mutations remain in the CLI until separately designed

Each later slice still requires a reviewed design, a written implementation plan, and acceptance evidence.
