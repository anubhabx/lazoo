# Lazoo Native Provider Adapters Design

**Status:** Approved by the owner-reviewed project brief and the 2026-08-30 autonomous provider-connector request

**Scope:** Backend-only native adapters for Codex, OpenCode, Grok Build, Antigravity/agy, and Claude Code. No desktop UI changes.

## Outcome

Lazoo gains a versioned native-provider boundary that can discover installations, report truthful readiness, start or resume native sessions, submit turns, normalize progress, cancel work, and stop owned child processes. The implementation preserves each harness's native models, configuration, tools, MCP/plugins/skills, permissions, authentication, and session identifiers.

This slice does not add employees, delegation, worktrees, approvals, the durable team message bus, or terminal takeover. Those systems will consume the adapter contract later. The daemon and CLI expose read-only provider truth and opt-in smoke diagnostics; they do not add provider data to the desktop snapshot.

## Architecture

Create a focused `lazoo-providers` crate. Public contract types describe provider identity, executable candidates, capability truth, authentication state, verification state, probe evidence, session requests, normalized events, and stable adapter errors. Provider modules own native command construction and protocol parsing. A registry applies the same contract to all five modules and allows daemon/CLI discovery without provider-name heuristics.

Two reusable transports sit below provider modules:

- A line-delimited bidirectional JSON-RPC transport for Codex App Server. It correlates responses by request ID while forwarding notifications and provider-initiated requests.
- The official Agent Client Protocol Rust SDK schema types for OpenCode and Grok Build, carried over Lazoo's bounded JSON-RPC process transport. The SDK's process helper cannot set a child working directory, so the shared Lazoo transport retains structured cwd, Windows process ownership, timeout, and stderr guarantees while official types define the wire payloads. Provider wrappers select native launch commands and retain provider-specific capability evidence.

Claude Code and agy use long-lived `stream-json` input/output processes. They share only safe NDJSON process plumbing; their schemas and event normalization remain separate because their wire contracts differ.

Every child process is spawned directly with structured arguments, redirected standard streams, `kill_on_drop`, a bounded startup/turn/shutdown timeout, and a continuously drained stderr pipe. This slice owns the direct child; Windows Job Object and ConPTY ownership remain the later employee-lifecycle slice and are not falsely claimed here.

## Versioned contract

`ADAPTER_CONTRACT_V1` is independent of the control IPC protocol. Each adapter publishes:

- `ProviderKind`: `codex`, `opencode`, `grok-build`, `antigravity`, or `claude-code`.
- Discovery evidence: absolute executable path, source (`inherited-path`, persisted user/machine PATH, or known install location), and candidate priority.
- Probe evidence: installed version, protocol compatibility, authentication readiness when safely detectable, degradation reason, and the exact capabilities actually negotiated or verified.
- Lifecycle: start new, resume when supported, turn, cancel, and graceful stop.
- Normalized events: session started, turn started, text/thought delta, tool/terminal/permission/progress update, usage, turn completed, cancelled, provider error, and process exit. Each event may retain a redacted raw JSON payload.

Capabilities default to false. Discovery alone yields `detected`; a protocol handshake without a model-backed turn yields `configured` or `unverified` according to the evidence; incompatible or failed health checks yield `degraded`; only a fresh model-backed conformance run may yield `verified`. A missing executable is `not-detected` and is never routed.

## Provider mappings

### Codex

Launch `codex app-server --listen stdio://`, send `initialize`, then `initialized`. Use `thread/start`, `thread/resume`, `turn/start`, and `turn/interrupt`, and consume thread/turn/item notifications. Vendor stable JSON schemas generated by the installed CLI only as conformance fixtures; runtime parsing remains tolerant of additive provider fields while required identity/status fields stay strict. Non-interactive JSON execution is diagnostic fallback only.

### OpenCode

Launch `opencode acp` and negotiate ACP v1 over stdio. Map ACP session creation/load, prompt, updates, permission requests, cancellation, and close. Missing progress after nominal prompt acceptance is a deadline failure, not success.

### Grok Build

Launch `grok agent stdio` and negotiate ACP v1. Map the same ACP lifecycle but preserve Grok-specific model, reasoning, permission, terminal, and resume evidence. ACP capability negotiation decides support; the provider name does not.

### Antigravity

Launch `agy --print --input-format stream-json --output-format stream-json` with an explicit project/workspace context. Send one NDJSON user message per turn, persist returned conversation identifiers, use `--conversation` on resume, and normalize assistant, tool, usage, result, and error records. Until a model-backed run completes, report `unverified`.

### Claude Code

Launch `claude --print --input-format stream-json --output-format stream-json --replay-user-messages` with explicit permission and workspace arguments. Use a caller-supplied UUID for new sessions and `--resume` for continuation. Normalize system, assistant, stream, tool, result, permission, and error records. Native Anthropic subscription readiness and configured external-endpoint readiness are separate probe evidence; one must not overwrite the other.

## Daemon and CLI boundary

Add `provider.list` and `provider.probe` control methods plus `lazooctl provider list|probe`. These are read-only and bounded. An opt-in `lazooctl provider smoke <provider> --prompt <text>` diagnostic exercises one provider session through the daemon and returns a concise transcript/evidence record; it never runs automatically from `provider list` and never appears in the desktop snapshot.

The daemon holds a registry, not live employee sessions. Smoke runs are diagnostic and single-turn. Persistent employee/session ownership belongs to the employee lifecycle slice.

## Safety and privacy

- Never read, copy, log, or migrate provider credentials.
- Redact environment values, authorization material, and provider raw fields with secret-like keys before persistence or display.
- Resolve executables from inherited PATH, persisted Windows PATH values, and provider-specific known locations; canonicalize candidates before use.
- Never interpolate a shell command. Pass executable and arguments directly.
- Default permission behavior remains provider-native/ask-like. Smoke prompts use no auto-approve flags.
- Bound stdout/stderr record size, total transcript bytes, startup time, progress time, turn time, and shutdown time.
- A live smoke call is explicit because it may consume provider quota. Contract and fixture tests make no model calls.

## Testing and acceptance

Each adapter follows red-green-refactor independently:

1. Synthetic discovery and recorded protocol fixtures prove parsing, capability negotiation, event normalization, cancellation, and error mapping.
2. Fake child-process fixtures prove startup, streaming, progress deadlines, bounded shutdown, and redaction without external accounts.
3. Live smoke tests run one provider at a time against installed executables. Failures remain provider-specific evidence; they do not invalidate other adapters.
4. Full workspace tests, check, Clippy, formatting, release build, first-slice acceptance, and provider-adapter acceptance run before completion.

The acceptance manifest records executable path hash metadata (not secrets), version, handshake outcome, model-backed outcome, supported/unsupported capability evidence, blocker strings, and timestamps. A provider is never labeled verified when its live gate was skipped or blocked.
