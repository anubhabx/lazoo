## Completed backend baseline

- Schema is 15. An incident promoted to `priority` on a task below an active root (and not about that root's own employee) opens the lead's remediation window: `escalation: lead` with `remediationDeadlineAt` five minutes after promotion, named in the lead's `status` notice. Any other promotion goes to the user at once (`escalation: user`, reason `no-lead`), and every unresolved priority incident from before schema 12 was moved to the user (`schema-upgrade`).
- Inside the window the lead may apply at most two remedies through the ninth tool, `incident_remedy`: `cancel-task` cancels the incident's task (a direct child of the lead's root) with the lead as actor, and an in-flight dispatch turn is asked to cancel exactly as `task.cancel` does; `redelegate-task` sends a `failed` or `cancelled` child's objective out again through every delegation guard. Each remedy commits with its action and is listed under the incident's `remedies`; a refused one consumes no attempt.
- `remediation_verdict` in `lazoo-domain` is the whole rule. The daemon's timed sweep (`run_timed_sweeps`, every 15 seconds beside idle suspension) closes passed windows: no recurrence since the lead's last remedy makes the incident `remediated`; anything else unresolved becomes `escalation: user` with `no-remedy` or `recurred-after-remedy`. A recurrence after the second remedy, or after a remediated window, reaches the user in the transaction that records it. Escalation never acknowledges, resolves, retries, restarts, or reassigns anything.
- `lazooctl incident list --escalation user` lists the priority notifications; `incident show` includes the remedies.
- Section 14.2's default thresholds apply per code (no schema change): `LZ-SESSION-STALLED`, `LZ-DAEMON-UNAVAILABLE`, and an `LZ-PROCESS-EXIT` tied to a task are promoted by their first occurrence (the incident is born `priority` with its escalation, and its event is `incident.escalated`), any other `LZ-PROCESS-EXIT` by its second, and every other code by three inside five minutes. A dead-lettered priority message is promoted by its first (schema 14). Schema 15 lets the local user override any code's occurrences and window (`incident.threshold.list/set/reset`, `lazooctl incident threshold`; 1 to 100 occurrences inside 60 to 86400 seconds) from the next occurrence; a death under assigned work and a dead-lettered priority message promote at once whatever is configured, nothing is ever demoted, and no tool can read or set a threshold.
- Schema 13 announces each open incident that reaches `escalation: user` on the Windows desktop at most once, through `UserNotifier` (default `NativeNotifier`, the keeper's toast) from the timed sweep: claimed before it is shown, one notification per pass (a count when several arrive together), recorded as `shown` or `failed` and never retried, and settled as `keeper` without a second notification for a keeper record.
- `task_wait` and a `message_send` waiting for its reply wake on the daemon's own store write instead of re-reading the store every 250 ms: `publish_events`, which follows every store write, wakes one `Notify`, and each wait registers for it before it reads the store and parks on it or its unchanged deadline. No schema, tool, result, or evidence change.
- Schema 14 gives every message envelope a `priority` (`normal` or `priority`). The incident notice to a lead is always `priority`; `message.send` and `lazooctl message send --priority` let the user send one; delegations, results, peer messages, replies, and user turns are `normal`, and no tool can set it. `raise_incident` reads the message's priority and dead letter itself, and one dead-lettered priority message promotes `LZ-MESSAGE-DEADLETTER` at once. `message.fail` raises it immediately; `note_priority_dead_letters_once` (startup and the head of every timed sweep) raises it for every other priority dead letter, keyed `dead-letter:<message>:<attempt>` so each dead letter is reported once. Incident notices written before schema 14 became `priority`.
- The desktop Inbox read model is served without a schema change. `inbox.list { filter: all | approvals | permissions | incidents | resolved, limit?: 1..500 (200), before? }` and `inbox.counts {}` derive the Inbox on every call from the ledgers that already exist: a pending approval, a `proposed` task, an `uncertain` task, and an open incident with `escalation: user` are `action-required` and count toward the badge (`counts.unresolved`); an open incident in a lead's window is `watching` with its `remediationDeadlineAt` and never counts; an acknowledged escalation is visible but uncounted; a decided approval, a terminal task that was once `proposed` or `uncertain`, and a resolved or remediated escalation are the `resolved` archive, newest change first, paged with the opaque `nextBefore` cursor. Unresolved filters order counted items first, then the nearest deadline, then oldest first. Every item carries its source row's `id`, `revision`, and `state`, Lazoo's own `title` and `requiredAction`, a deep-link `scope` (null `projectId` is Home), a kind-specific `detail`, and its applicable `actions` as data naming an existing revision-checked RPC (`approval.decide`, `task.accept`, a user `task.cancel`, `task.resolve` with the task's own failure for `failed`, `incident.acknowledge`, `incident.resolve`; an uncertain task with an unfinished descendant offers only `resolve-failed`, the one resolution `task.resolve` accepts for it, from `inbox_sources`' `active_descendants`); the caller adds a fresh `idempotencyKey`. `eventHighWater` is the sequence the result reflects. `kind: permission` and the Permissions filter are reserved and empty until terminal permission passthrough exists. `lazooctl inbox list|counts` maps to the two methods. Nothing is stored, no event or mutation exists, and no collaboration tool can read it. The whole rule is `lazoo_domain::inbox`; the store reads are `inbox_sources` and `inbox_archive`.
- Resource accounting (brief section 20) is displayed without a schema change. `system.resources {}` reports the daemon's own process (`pid`, `bootId`, `uptimeMillis`, `cpuMillis` with its user and kernel parts, `workingSetBytes`, `peakWorkingSetBytes`, `handleCount`, `liveSessions`, `sampledAt`) through `lazoo_runtime::current_process_accounting`; `session.resources { id }` reports a session live in this daemon from the Job Object Lazoo already owns for its native process tree (`activeProcesses`, `totalProcesses`, `cpuMillis` and parts, `peakProcessMemoryBytes`, `peakJobMemoryBytes`, beside `employeeId`, `provider`, `nativeHostPid`, `sampledAt`) through `JobObject::accounting` and `ProviderSession::resources`, and refuses any other session with `LZ-SESSION-NOT-LIVE`. Both are point samples: nothing is stored, no event is emitted, no limit is set on any job, a provider's use is never counted against the daemon's, and `desktop.snapshot`, `system.status`, `session.show`, and `session.list` are unchanged. `lazooctl system resources` and `lazooctl session resources <id>` map to the two methods.
- `conversation.rename { id, expectedRevision, title | null }` (`lazooctl conversation rename`) sets or clears a conversation's title, the one mutation the information architecture's section 6.3 requires that did not exist (titles are user-editable). No schema change: the title column existed. Naturally idempotent (the same title again changes nothing and emits no event, whatever revision is cited); a different title needs the current revision (`LZ-CONVERSATION-STALE` carries it); every change is a `conversation.renamed` event with the previous title. No tool can rename a conversation.
- `provider.config {}` (`lazooctl provider config`) is read-only configuration discovery, the first five steps of brief section 16.1: per provider, the known file (`CODEX_HOME` or `~/.codex/config.toml`; `~/.claude.json`; `~/.config/opencode/opencode.json`) with `exists`, `parsed`, and an error that never quotes the file; every MCP server as one `DiscoveredIntegration` (`transport` stdio or http, `command`/`args` or `url`, `enabled`, `secretKeys` naming environment variables and headers and `url-query` when a query string was stripped, a SHA-256 `identity` over the normalized transport, command, arguments, and URL, `source`); `duplicates` (equal identities), `conflicts` (same name, different identity), and `unsupported` (Grok Build and Antigravity, and entries with neither command nor URL). `DiscoveryEnvironment` carries `config_home` (`USERPROFILE`) and `codex_home` (`CODEX_HOME`) so tests use fixture profiles. ## Guardrails

- Preserve the Windows-first, local-first, single-user boundary.
- Reuse the durable record-first ledgers and native provider evidence.
- A notice or peer message is derived evidence: the task, message, and incident rows it points at stay authoritative, and neither ever retries work, restarts anything, re-authenticates, changes authority, or deletes data.
- Configuration discovery is a reading too: never write, move, or back up a provider file in this slice, never report a secret value, and never let a tool read a provider's configuration.
- A resource sample is a reading, not a record: never store it, never raise an incident from it, never limit or throttle a job because of it in this slice, and never fold a provider tree's use into Lazoo's own.
- The workspace read models are derived evidence too: never store a marker, a lifecycle, a card state, or a dismissal, never report a state a durable row does not support (`unknown` is only an `uncertain` row), and never let a card or header name an action its RPC would refuse now, name a different actor than the user, or skip `expectedRevision`.
- The Inbox is derived evidence too: never store it, never give it read state, never count anything but `action-required` on the badge, never add an Inbox-specific mutation, never let an item's action name a different actor or skip `expectedRevision`, and never let a tool read it.
- Never merge, summarise, or truncate one notice into another; a coalesced turn carries each notice whole and each keeps its own message row and evidence.
- Never let employee-authored traffic start a provider process on its own. Only a recorded notice turn for an employee the user set to `notice-turns` may, once per turn, on that employee's own task, and the session stops with the turn; everyone else waits for the local user. No tool can read or set the policy.
- Never stop a session that has an unfinished turn on it, and never stop a session for idleness unless its own employee's timeout, set by the user, has passed. No tool can read or set the idle timeout.
- Never let a lead apply more than two remedies to one incident, after its window, outside a direct child of its own root task, or as anything but itself; never record a remedy whose action did not commit; never let a remedy or an escalation acknowledge or resolve an incident, start a provider process, or redelegate an `uncertain` task.
- A notice or peer turn runs under the recipient task's effective authority; governed actions inside it still flow through the schema-8 approval gate, and neither a tool result nor a peer message is ever an approval.
- Never let a tool name a different actor, widen authority, or bypass a store guard; the daemon fixes the actor to the turn's recipient endpoint.
- Never deliver a peer message to a task that has not started, never let a peer-only turn complete a task, and never reuse a closed notice turn.
- Never declare tools on a resumed Codex thread; every activation is a fresh `thread/start`, and the adapter fails closed until Codex accepts `dynamicTools` on `thread/resume`.
- Never retry an activation, a suspension stop, an uncertain dispatch, a failed notice or peer turn, or an expired approval automatically.
- Never delete or rewrite a retained task worktree without an explicit cleanup contract.
- Keep UI, ConPTY, session-wide grants, managed memory, scheduling, resource governance, other-provider expansion, and live model use outside this completed slice.
